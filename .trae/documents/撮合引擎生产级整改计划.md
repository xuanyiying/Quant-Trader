## 结论（对照你给的“完整撮合引擎”要求）
当前 `backend/internal/matching` 的实现属于“可运行的撮合原型”，**不满足生产环境**要求，且与需求清单存在结构性缺口：

- **并发与一致性缺口**：没有真正做到“单品种单线程撮合”，也没有加锁保护，任何并发访问都会 data race。
- **审计与可追溯缺口**：成交 ID/时间戳语义不正确，缺少事件流与可回放序列。
- **正确性缺陷（P0 bug）**：盘口价位聚合量 `TotalVolume` 在部分成交时不会更新，会导致深度/可成交量相关逻辑错误。

## 整改目标（生产级最小闭环）
- 语义清晰：Limit/Market/IOC/FOK 的终态、拒单原因码、撮合时间戳、唯一序列号。
- 单写者：每 symbol 独立 goroutine + channel 路由，撮合路径无锁。
- 可审计：不可变事件流（OrderAccepted/Open/Trade/Cancel/Reject…）可落库/回放。
- 正确性优先：修复聚合量等账面错误；再做性能优化。

## 计划（按优先级落地，避免大改返工）
### 1) P0：修复正确性与语义漏洞
- 修复 `OrderQueue.TotalVolume` 在部分成交时同步扣减。
- 明确并实现 FOK/IOC/Market 语义：
  - FOK：撮合前可成交量检查（不足则 0 成交拒绝/撤销）。
  - IOC：部分成交允许，但剩余必须“取消剩余”，终态可表达（新增状态或事件）。
  - Market：流动性不足时的策略（Fill-and-Kill 或 RejectIfNotFullyFilled），并返回明确结果。
- 修正 Trade 的 `ID` 与 `Timestamp`：引入 per-symbol 单调序列（matchSeq），时间戳取撮合时刻（可注入 now 便于回放/测试）。

### 2) P0：实现真正的“单品种单线程撮合”
- `Engine` 增加 per-symbol worker：
  - `SubmitOrder/CancelOrder` 走 channel，worker 内部持有 `OrderBook`，外部不直接拿可变指针。
  - `GetOrderBook` 改为快照输出（避免外部并发读写同一结构）。
- 加入 `go test -race` 覆盖关键路径，确保无 data race。

### 3) P1：补齐生产必需的校验与量化
- per-symbol 配置：`tickSize/lotSize/minQty/minNotional`。
- 接单校验：Price/Qty>0、按 tick/lot 对齐（拒单或量化，策略明确）。

### 4) P1：引入事件模型 + 审计/回放接口（最小可用）
- 定义事件结构：OrderEvent、TradeEvent（携带 eventID、seq、ts、reason）。
- 提供订阅输出（channel），由上层写入 DB/NATS/日志。

### 5) P2：扩展到你需求清单的“完整模块”
- 订单类型扩展：Stop/TakeProfit/Iceberg（含展示量释放规则）。
- 集合竞价：时间窗收集 + 统一定价/分配。
- 市场状态机：PreOpen/OpenAuction/Continuous/Closing/Closed + 熔断。
- 风控模块接口：涨跌停、频率控制、大额预警、反操纵（先做框架与钩子）。
- 清算算法：VWAP、手续费阶梯、持仓 PnL（可从事件流派生）。
